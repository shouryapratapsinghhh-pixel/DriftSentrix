# Model Card — DriftSentrix

## Intended use

Detecting anomalies in multivariate time-series streams (sensor telemetry,
server/machine metrics) where labeled anomalies are scarce or unavailable at
deployment time. Intended as a **portfolio/research artifact** demonstrating
an honest evaluation methodology and a full detection-to-serving pipeline —
not a production-hardened system as shipped. See "Failure modes" below before
using any of this on decisions that matter.

## Models

| Model | Type | Trained on |
|---|---|---|
| Random | sanity baseline | n/a |
| Z-score | statistical, window=1 | train mean/std |
| EWMA | statistical, recurrent | train mean/std, exponential decay |
| Isolation Forest | tree ensemble | train (unsupervised) |
| PCA | reconstruction error | train (unsupervised) |
| LSTM-AE | deep, window=32 | train (reconstruction, MSE) |
| Transformer-AE | deep, window=32 | train (reconstruction, MSE) |

All models are trained **unsupervised**: `fit(train)` never sees anomaly
labels, only assumed-clean data. Labels are used solely for evaluation and
for the (explicitly non-deployable) oracle threshold.

## Training data

This repo's committed results are on **synthetic data** (`data/loaders.py:
make_synthetic`) — sinusoidal multivariate signals with injected
contiguous mean/variance-shift anomaly segments, generated fresh (no external
download) so results are reproducible from a fresh clone with zero setup.
Loaders for SMD and NASA SMAP/MSL are implemented and unit-tested but require
downloading those datasets locally (`data/README.md`); results on them are
not included here because they haven't been run in this environment — see
`docs/ASSUMPTIONS.md`.

## Metrics

Point-F1, point-adjusted F1, and event-F1, always reported together — see
`docs/EVALUATION.md` for why PA-F1 alone is misleading. See the README's
Results section (machine-generated by `scripts/build_readme_results.py`,
never hand-typed) for current numbers.

## Limitations

- Results are on synthetic data with a specific, hand-designed anomaly
  injection process (contiguous mean/variance shifts). Real-world anomalies
  (SMD/SMAP-MSL, or any production stream) may look structurally different;
  relative model rankings here should not be assumed to transfer.
- Deep models (LSTM-AE, Transformer-AE) were trained with small
  hyperparameters (window=32, hidden/d_model=64, ≤30 epochs) suited to fast
  CPU iteration on this repo's synthetic data — not tuned for any specific
  real dataset or production SLA.
- The streaming service shares one fitted detector instance across all
  entities. This is safe for the deep models (pure function of fixed weights
  + input window) but would NOT be safe for a stateful detector like EWMA if
  it were ever exposed the same way (see `serve/state.py`'s docstring) —
  each entity would need its own detector instance.
- POT and PSI both need enough data to be trustworthy (see `docs/EVALUATION.md`
  and `docs/ASSUMPTIONS.md`); both are documented to warn rather than fail
  silently when starved of data, but a caller ignoring the warning can still
  get a poorly calibrated threshold or a noisy drift signal.

## Failure modes

- **Regime change not covered by training data**: since every model is
  trained only on "clean" train data assumed representative of normal
  operation, a legitimate but unseen operating regime (e.g. a new but
  benign operating mode) will likely be flagged as anomalous. The drift
  monitor (Phase 7) is intended to catch this class of issue at the input
  level, distinct from the anomaly detector itself.
- **Small-window drift false alarms**: see the PSI small-sample-noise note
  above and in `monitor/drift.py` — a `DriftMonitor` queried before it has
  accumulated enough points can report `warn`/`alert` on pure sampling
  noise, not real drift.
- **POT with sparse validation data**: observed directly in this repo's own
  export runs (`eval/pot.py`'s `MIN_EXCESSES_FOR_FIT` warning fired on a
  small validation slice during development) — a threshold from POT should
  not be trusted blindly when the warning is logged.

## Ethical notes

No personal or sensitive data is used or required — all committed results
are on synthetic data generated by this repo. If applied to real
sensor/server telemetry in a production setting, standard operational
considerations apply: false negatives on safety-critical equipment carry
real risk, and any deployment should validate against domain-specific
labeled incidents before being trusted for automated action (as opposed to
alerting a human).
